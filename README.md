# 🔐 팀 비밀 금고 (제로지식 시크릿 볼트)

> API 키·비밀번호 같은 민감 정보를 팀원과 안전하게 공유하되, **서버 운영자조차 평문을 볼 수 없는** 제로지식(Zero-Knowledge) 금고.
> 아이펠 학습 실습 — 백엔드/프론트엔드 분리 · 해시/솔트 · 공개키 · 세션키(대칭키)를 억지 없이 한 흐름에 녹였다.

---

## 1. 무엇을 해결하나

개발팀은 API 키·DB 비밀번호·토큰을 매일 주고받는다. 그런데 이걸 **카톡·메일·슬랙**으로 보내면 대화 기록·서버·백업에 **평문**으로 남는다. 한 곳만 털려도 전부 유출된다.

이 서비스는 그 문제를 이렇게 푼다:
- 시크릿은 **브라우저 안에서 암호화**된 뒤에야 서버로 간다. 서버는 암호문만 본다.
- 특정 팀원에게만 **그 사람 열쇠로 다시 봉인**해서 공유한다.
- **서버 관리자(=나)조차** DB를 통째로 열어봐도 평문을 못 본다.

실제 Bitwarden이 쓰는 구조의 축소판이다.

---

## 2. 어떻게 생겼나 (사용 흐름)

화면은 하나(단일 페이지)이고, 로그인 전/후로 모습이 바뀐다.

1. **회원가입** — 사용자명 + 마스터 비밀번호. 가입 순간 브라우저가 조용히 RSA 열쇠 한 쌍을 만든다.
2. **로그인** — 같은 정보로 로그인. 개인키가 브라우저 메모리에만 올라온다.
3. **새 시크릿 추가** — 제목(평문 라벨) + 내용. [저장]을 누르면 내용이 암호화되어 전송된다.
4. **보기** — 목록의 [보기]를 누르면 그 자리에서 복호화되어 값이 뜬다. [복사]로 클립보드에 복사.
5. **공유** — [공유] → 팀원 사용자명 입력. 그 사람 금고에 나타난다.
6. **삭제** — 소유자만 삭제 가능. 공유받은 사람의 접근도 함께 사라진다.

## 3. 보안 모델 — 배운 개념이 실제로 일하는 곳

### 회원가입 (전부 브라우저에서 계산)
1. 마스터 비번 `P`와 랜덤 `salt`로 **PBKDF2**를 2번 돌려 키를 두 갈래로 만든다.
   - **authKey**: 로그인 증명값 → 서버로 감. 서버는 이걸 다시 **bcrypt로 해시**해 저장.
   - **vaultKey**: 절대 서버로 안 감. 내 개인키를 잠그는 대칭키.
2. **RSA 키쌍** 생성 → 공개키는 그대로, 개인키는 vaultKey로 **AES-GCM 암호화**해서 서버에 저장.

### 시크릿 저장
1. 랜덤 **대칭키 K**(세션키) 생성 → 내용을 **AES-GCM**으로 암호화.
2. K를 **내 공개키로 RSA-OAEP 봉인** → 암호문 + 봉인된 K만 전송.

### 팀원 공유
- 대상의 공개키를 가져와 **K를 그 사람 공개키로 다시 봉인** → 대상만 자기 개인키로 K를 풀 수 있다.

### 개념 매핑
| 배운 개념 | 이 서비스에서 하는 일 |
|---|---|
| **해시/솔트** | 서버가 authKey를 bcrypt(솔트 자동)로 저장 → DB 유출돼도 비번 복원 불가 |
| **공개키/개인키** | 대칭키를 봉인·공유. 서버는 공개키·암호문만 봄 |
| **세션키(대칭키)** | AES-GCM으로 시크릿 본문을 실제 암호화(빠름·대용량) |
| **세션 토큰** | Flask 쿠키 세션으로 로그인 유지 |
| **백/프론트 분리** | 프론트=모든 암호 연산, 백=암호문·해시·세션만 |

## 4. 검증 결과 (실제 실행으로 확인함)

프론트 `암호.js`와 **완전히 동일한 알고리즘**으로 실행 중인 서버에 종단간 테스트를 돌려 다음을 증명했다:

| # | 검증 항목 | 결과 |
|---|---|---|
| 1 | 저장 시 서버로 나가는 데이터에 **평문 없음** (암호문만) | ✅ |
| 2 | **마스터 비번**이 어떤 요청에도 안 나감 | ✅ |
| 3 | 철수 → 영희 공유 후 **영희가 자기 개인키로 복호화 성공** | ✅ |
| 4 | 권한 없는 제3자는 목록도 안 보이고, 암호문을 훔쳐도 **복호화 실패** | ✅ |
| 5 | 서버 DB 파일을 직접 열어도 **평문 시크릿·비번 없음** (암호문·bcrypt 해시만) | ✅ |

> 같은 시크릿이라도 철수와 영희의 봉인된 열쇠(wrapped_key)는 **서로 다르다** — 각자 공개키로 따로 봉인하기 때문. 공개키 암호가 실제로 일하고 있다는 증거.

재현: `node 공유암호화_증거테스트.mjs` (서버가 켜져 있어야 함)

## 5. 실행 방법 (Windows / git-bash)

```bash
# 1) 가상환경 생성·활성화
python -m venv .venv
source .venv/Scripts/activate

# 2) 설치
pip install -r backend/requirements.txt

# 3) (권장) 세션키 설정 — 안 하면 실행마다 임시키(재시작 시 로그인 풀림)
python -c "import secrets; print('SECRET_KEY=' + secrets.token_hex(32))" > .env

# 4) 실행
cd backend && python app.py
#   → http://127.0.0.1:5000
```

## 7. 이 설계의 트레이드오프 (꼭 이해해야 할 부분)

제로지식은 공짜가 아니다. **"서버도 못 여는 금고"의 대가**로 다음을 감수한다:

- **마스터 비번을 잊어도 복구 키로 복구 가능(v2).** 단 복구 키까지 잃으면 아무도 못 연다(제로지식의 본질).
- **PC 초기화는 안전하다.** 데이터는 서버에 있으므로, 마스터 비번만 기억하면 다른 PC에서 로그인 → 복구된다. 진짜 위험은 "비번 분실"이지 "기기 분실"이 아니다.
- **서버 보안의 무게추가 가벼워진다.** 서버가 털려도 암호문·해시뿐이라 열 수 없다. 대신 **사용자의 비번 관리**가 가장 중요해진다.

---

## 8. ⚠️ 주의 / 한계 (v1)

- **로컬 실습 전용**: `127.0.0.1`에서만. 실제 배포하려면 **HTTPS 필수**(WebCrypto가 secure context를 요구).
- `salt` 조회 API로 사용자명 존재 여부가 노출됨(실습 단순화, 감수).
- 제목(title)은 평문 저장 — 민감정보를 제목에 넣지 말 것.
- 2FA·비밀번호 강도 검사·권한 등급·키 회수(revocation)는 v1 제외.

---

## 9. ✅ 복구 키(Recovery Key) — 구현 완료 (v2)

초기 버전은 마스터 비번을 잊으면 복구가 불가능했다. v2에서 **복구 키 기능을 구현**했다:

- 가입 시 **160비트 무작위 복구 키**(`XXXX-XXXX-...` 8그룹)를 1회 발급. 개인키를 마스터 비번과 복구 키로 **각각 봉인해 두 사본**을 서버에 둔다.
- 비번을 잊으면 **복구 키로 개인키를 되살리고 새 마스터 비번을 설정**한다. 개인키가 바뀌지 않으므로 **기존 시크릿·공유가 전부 그대로 유효**하다.
- 복구 키도 서버로 원본이 가지 않는다(제로지식 유지). 서버엔 bcrypt 해시와 암호문만.
- 로그인 상태에서 **복구 키 재발급**도 가능.

### 검증 결과 (실제 실행)
| # | 항목 | 결과 |
|---|---|---|
| 1 | 가입 시 복구 키 발급 + DB에 복구 컬럼 채워짐 | ✅ |
| 2 | 비번 분실 → 복구 키로 새 비번 설정 → 새 비번 로그인 → **기존 시크릿 복호화 성공** | ✅ |
| 3 | 복구 후 옛 비번은 거부됨(401) | ✅ |
| 4 | 틀린 복구 키는 거부됨(401) | ✅ |
| 5 | DB에 복구 키 원본·평문 없음(bcrypt 해시·암호문만) | ✅ |
| 6 | 기존(복구 키 없는) 계정도 무손실 마이그레이션 | ✅ |

재현: `node 복구키_증거테스트.mjs`

### 트레이드오프 (핵심 학습 포인트)
복구 경로가 늘면 공격 표면도 는다. **복구 키가 유출되면 마스터 비번 유출과 동급**이다. 대신 256비트급 무작위라 무차별 대입은 비현실적. "보안(제로지식) ↔ 복구성"의 긴장 관계를 눈으로 확인하는 것이 이 기능의 학습 목표다.

상세 설계: `📘복구키_기능명세서.md`

## 10. 배운 점

- WebCrypto만으로 PBKDF2·AES-GCM·RSA-OAEP를 외부 라이브러리 없이 다 처리할 수 있다.
- 화면을 여러 HTML로 나누면 페이지 이동 시 메모리의 개인키가 사라진다 → **단일 페이지 전환** 방식이 제로지식 모델과 더 잘 맞는다.
- "암호화했다"는 주장은 **서버로 나가는 실제 데이터와 DB 파일을 직접 열어** 확인해야 믿을 수 있다.
